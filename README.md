# Library Management System

A NestJS + Prisma + PostgreSQL data layer for a library book catalog.

> This is an unofficial academic project. Configure your own PostgreSQL connection locally; never commit database credentials.

## Requirements

- Node.js and npm
- PostgreSQL database (Render is supported)
- Prisma 7
- NestJS

## Setup

1. Copy the `api` folder contents in this bundle into the existing `api` folder generated by NestJS. Keep your existing NestJS `package.json` and merge the dependencies/scripts shown below rather than replacing the whole file.
2. In `api`, install the required packages:

   ```bash
   npm install @prisma/client@7 @prisma/adapter-pg@7 pg dotenv
   npm install -D prisma@7 tsx @types/pg
   ```

3. Copy `.env.example` to `.env` inside `api` and set `DATABASE_URL` to your Render **External Database URL**. External Render connections require TLS; keep the `?sslmode=require` query parameter. Do not share or commit `.env`.
4. Ensure these scripts are present in `api/package.json`:

   ```json
   {
     "prisma:generate": "prisma generate",
     "db:migrate": "prisma migrate dev --name init",
     "db:seed": "prisma db seed"
   }
   ```

5. From the `api` directory, run:

   ```bash
   npx prisma generate
   npx prisma migrate dev --name init
   npx prisma db seed
   ```

6. Start the NestJS app with `npm run start:dev`.

## Render PostgreSQL

In the Render dashboard, open your PostgreSQL database and select **Connect**. Use the **External Database URL** for local development. Put it in `api/.env` as `DATABASE_URL`. For a service deployed on Render in the same region and workspace, prefer the **Internal Database URL**.

Example shape only (not a real credential):

```env
DATABASE_URL="postgresql://USER:PASSWORD@HOST/DBNAME?sslmode=require"
```

## Schema Decisions

`Book` references `Genre` through the `genreId` foreign key instead of embedding genre details in every book. This is a normalized relational design: a genre is stored once and can be related to many books. It avoids duplicated genre names, makes genre updates consistent, and allows PostgreSQL foreign-key constraints to prevent books from referring to nonexistent genres. The Prisma `@relation` declaration makes this relationship explicit in the application model.

`User.role` uses a Prisma enum (`PATRON` or `LIBRARIAN`) so only the supported role values can be stored. `email` is unique so one account cannot be registered under the same email more than once.

## Seed data

The seed script creates four genres and at least fifteen books. It uses upserts for genres and clears/recreates the catalog books so rerunning the seed produces a predictable sample catalog.

## Optional Review relation

`Review` demonstrates a many-to-one relation to both `Book` and `User`. A review belongs to one book and one user; the `(bookId, userId)` unique constraint prevents a user from submitting duplicate reviews for the same book.

## Prisma vs. document databases

In Prisma with PostgreSQL, relationships are represented using foreign keys and explicit relation fields. In a document database, related information is often embedded inside a document or linked by application-managed identifiers. The relational approach makes referential integrity easier to enforce at the database level, while embedding can make some read operations simpler but may duplicate data.

## Security

- Keep `api/.env` private and out of Git.
- Commit `api/.env.example` with a placeholder only.
- Never paste a full database URL or password into public issues, screenshots, or chat.
